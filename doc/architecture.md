# Architecture

## Current

```
inocube.sk (Netlify, static)          AWS eu-central-1, stack "inocube-backend" (SAM)
  contact form  ── (not connected yet) ─▶  API Gateway REST, stage Prod
                                             ├─ GET /health ─▶ Lambda HealthFunction (python3.14, arm64)
                                             └─ POST /leads ─▶ Lambda LeadsFunction ─▶ DynamoDB "inocube-leads"
```

## Target (after roadmap phase 5)

```
Browser ─▶ api.inocube.sk (API Gateway, throttling, CORS for inocube.sk)
             ├─ POST /leads ─▶ LeadsFunction ─▶ DynamoDB inocube-leads
             │                      └─▶ SES e-mail to owner
             └─ DynamoDB Stream ─▶ TriageFunction ─▶ Bedrock (EU) ─▶ summary + draft reply stored on lead
GitHub Actions (OIDC role) ─▶ sam deploy: staging on PR merge, prod on release
```

## Components

| Component | Resource | Notes |
|---|---|---|
| API | `ServerlessRestApi` (implicit SAM API), stage `Prod` | Base URL in stack output `ApiUrl` |
| Health | `HealthFunction`, `src/health/` | `GET /health` → `{"status":"ok"}` |
| Leads | `LeadsFunction`, `src/leads/` | `POST /leads`; `app.py` (HTTP) → `models.py` (pydantic) → `repository.py` (boto3) |
| Storage | `LeadsTable` = `inocube-leads` | PAY_PER_REQUEST, PK/SK + GSI1 + GSI2 |
| Tracing | X-Ray active on all functions | via `Globals` |

## API

| Endpoint | Request | Responses |
|---|---|---|
| `GET /health` | none | `200 {"status":"ok", ...}` |
| `POST /leads` | JSON `name` (1–200), `email` (valid address), `message` (1–5000); trimmed, unknown fields ignored | `201 {"lead_id","status"}`, `400 {"error","details":[{"field","message"}]}` (no input echoed), `500 {"error"}` |

No CORS, honeypot or throttling yet (roadmap phase 2b). Logs contain lead IDs and outcomes only, never PII.

## Data model

Single table, generic key names so one index can serve several entity types later.

| Access pattern | How |
|---|---|
| Save lead | `PutItem` PK=`LEAD#<id>`, SK=`LEAD#<id>` |
| Get lead by ID | `GetItem` on PK/SK |
| List leads newest first | `Query` GSI1, GSI1PK=`LEAD`, `ScanIndexForward=false` |
| Leads by e-mail | `Query` GSI2, GSI2PK=`EMAIL#<email>` |

Attributes on a lead: `lead_id`, `name`, `email`, `message`, `created_at` (ISO 8601 UTC), `status` (`NEW`).
GSI1 has a single partition key value (`LEAD`): a known hot-partition trade-off, fine at a few leads per
day (ADR 0005).

## Identity and access

- Humans: IAM Identity Center (SSO) users; permission sets `PowerUserAccess` (profile `inocube`) and
  `InocubeSamDeploy` (profile `inocube-deploy`, adds IAM role creation for SAM). ADR 0004.
- Lambdas: one execution role per function generated by SAM policy templates, scoped to the table.
  `LeadsFunction` has `DynamoDBWritePolicy` (PutItem/UpdateItem/BatchWriteItem on `inocube-leads`, no reads).
- CI (planned): GitHub OIDC → dedicated deploy role, no stored keys.
